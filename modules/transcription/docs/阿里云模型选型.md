## 1. 为什么长音频只剩一条路

阿里云百炼的非实时语音识别分成**两类**，差异不是"精度高低"而是**能不能装下课**：

| 档位 | 代表模型 | 音频上限 | 输入方式 |
| --- | --- | --- | --- |
| **长音频档** | `qwen-audio-3.0-asr-flash-filetrans`、`fun-asr`、`fun-asr-mtl`、`qwen3-asr-flash-filetrans`、`paraformer-v2` | **12 小时 / 2 GB** | **仅公网可访问的 URL** |
| 短音频档 | `qwen-audio-3.0-asr-flash`、`fun-asr-flash-2026-06-15`、`qwen3-asr-flash` | 5 分钟 / 2 GB（`qwen3-asr-flash` 是 10 MB） | URL **或 Base64** |

也就是说：**"能不能内联提交音频"与"能不能装下 45 分钟课"在阿里云是互斥的。**

官方 FAQ 原文（Paraformer 非实时 Python SDK 页）：

> **Q：是否支持Base64编码方式的音频？**
> 不支持Base64编码方式的音频。仅支持可通过公网访问的 URL 所指向的音频的识别，
> **不支持识别二进制流，也不支持直接识别本地文件**。

> **Q：如何将音频文件以公网可访问的URL形式提供？**
> ……推荐将音频上传至阿里云 OSS……使用RESTful API时，若录音文件存储在阿里云OSS，
> **支持使用以 `oss://` 为前缀的临时 URL**……临时 URL 有效期 48 小时，
> 过期后无法使用，**请勿用于生产环境**。

（`oss://` 临时 URL 那条路我们不走：文件上传凭证接口限流 100 QPS 且不支持扩容，
官方自己标注"请勿用于生产环境、高并发及压测场景"。）

## 2. 候选对照

课堂录播的实际约束：单节 45 分钟起、中文为主常混英文、师生对话、有学科专有名词。

| 模型 ID | 音频上限 | 输入 | 时间戳 | 说话人分离 | 热词/上下文 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **`qwen-audio-3.0-asr-flash-filetrans`** | **12h / 2GB** | 公网 URL | ✅ 句级+字级 | ✅ | ✅ 热词 + Prompt 上下文 | **选用** |
| `fun-asr` / `fun-asr-mtl` | 12h / 2GB | 公网 URL | ✅ | ✅ | ⚠️ 仅热词（无 Prompt 上下文） | 备选 |
| `fun-asr-2025-11-07` / `fun-asr-2025-08-25` | 12h / 2GB | 公网 URL | ✅ | ✅ | ⚠️ 仅热词 | 快照版，不必 |
| `qwen3-asr-flash-filetrans` | 12h / 2GB | 公网 URL | ✅ | ❌ | ❌（有情感识别） | 需要辨"谁在说"时不够 |
| `paraformer-v2` | 12h / 2GB | 公网 URL | ✅ | ✅ | ✅ | 上一代，官方建议迁移 |
| `qwen-audio-3.0-asr-flash` | **5 分钟** / 2GB | URL **或 Base64** | ✅ | ❌ | ✅ | 时长不够 |
| `fun-asr-flash-2026-06-15` | **5 分钟** / 2GB | URL **或 Base64** | ✅ | ❌ | ✅ | 时长不够 |
| `qwen3-asr-flash` | **5 分钟 / 10MB** | URL/Base64/本地路径 | ✅ | ❌ | ❌ | 时长与体积都不够 |
| `sensevoice-v1` | — | — | — | — | — | **即将下线**，不用 |
| `gummy-*` | — | — | — | — | — | **即将下线**，不用 |

选 `qwen-audio-3.0-asr-flash-filetrans` 的五个理由，按权重排：

1. **时长**。12 小时档是唯一能装下课堂录播的档位；5 分钟档即使支持内联也没用。
2. **时间戳到字级**。契约的 `segments[].startMs/endMs` 直接依赖它，后续"抬头"模块与幻灯片对齐也要靠它。
3. **Prompt 上下文注入 + 热词**。课程有专有名词（知识点、人名、公式），这是本模块
   `HotwordListBuilder` 与 `course-hotwords` 配置第一次真正有使用点的路径。
4. **说话人分离**。课堂是师生对话，区分说话人对后续内容分析有直接价值；
   官方建议开说话人分离时音频 ≤2 小时（本模块默认上限就是 2 小时，正好卡住）。
5. **`language_hints` 支持至多 4 个值**，中英混说的课可直接给 `["zh","en"]`。

### 与腾讯云的对比

| | TokenHub（当前默认） | 腾讯云标准 ASR | 阿里云 filetrans |
| --- | --- | --- | --- |
| 长音频输入 | 内联 base64 或 URL | 仅 URL | **仅 URL** |
| 源文件上限 | 未见文档上限（实测 4MB MP4 直接提交成功） | **1 GB**（URL 方式） | **2 GB** |
| 时长上限 | 未标注 | 5 小时 | 12 小时 |

## 3. 协议形状（✅ 已真机验证）

```
提交  POST https://dashscope.aliyuncs.com/api/v1/services/audio/asr/transcription
      Authorization: Bearer {DASHSCOPE_API_KEY}
      X-DashScope-Async: enable          ← 必须，缺它返回 403 AccessDenied（已实测）
      {"model":"qwen-audio-3.0-asr-flash-filetrans",
       "input":{"file_urls":["https://预签名地址/audio.wav"]},
       "parameters":{"channel_id":[0]}}  ← channel_id 必须是数组！见 §3.1

轮询  GET  https://dashscope.aliyuncs.com/api/v1/tasks/{task_id}
      → output.task_status ∈ {PENDING, RUNNING, SUCCEEDED, FAILED}
      → output.results[0].transcription_url     （仅 SUCCEEDED 时有）

取结果 GET {transcription_url}                （预签名，勿带 Bearer 头）
      → transcripts[].sentences[].begin_time / end_time   ← 毫秒整数
```

> ✅ **不需要 WorkspaceId**。官方推荐业务空间专属域名
> `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1`，但实测
> **公共域名 `dashscope.aliyuncs.com` 直接接受 workspace 形态的 Key**（`sk-ws-…`）并正常出结果。
> 专属域名仍建议在生产使用（官方称性能与稳定性更好），但它不是可用性的前提。
> 本模块的 `resolvedBaseUrl()` 仍是"配了 workspaceId 就改写"，
> 所以**两种域名都能工作**，不配也能跑。

### 3.1 六个已经踩过或必须避开的坑

按"踩到时的痛苦程度"排序，前两条是**真机才发现的**：

1. ⚠️ **`channel_id` 必须发数组，不能发标量**（真机踩到，代价是"看起来成功实则全失败"）：

   ```
   parameters: {"channel_id": 0}      → 提交 HTTP 200 + task_id（一切正常的样子）
                                      → 轮询 FAILED: "parameter.channel_id must be an array"
   parameters: {"channel_id": [0]}    → 提交 HTTP 200 → SUCCEEDED
   ```

   官方 HTTP API 参数表里 `channel_id` 的类型确实是 `list[int]`，
   但「结果说明」与常见示例都是单值语境（`"channels": [0]`、`"channel_id": 0`），
   照着写就会写成标量。**提交阶段完全看不出来**，只有轮询到 FAILED 才知道，
   而那时你已经有理由怀疑是音频、是额度、是模型——不会怀疑参数类型。
   本模块已加测试钉住（`AliyunAsrClientTest.channelIdMustBeAnArray`）。

2. ⚠️ **失败信息的两种形状，且音频不可达时几乎没有信息**：

   | 失败层 | 响应形状 | 可读性 |
   | --- | --- | --- |
   | 任务级（参数错） | `output.code` + `output.message`，**`results` 整个是 null** | 好，如 `parameter.channel_id must be an array` |
   | 任务级（音频不可达） | **只有 `output.code = "SERVER_ERROR"`，连 `message` 都没有** | 差，等于没说 |

   实测 `SERVER_ERROR` 唯一出现的场景就是引擎下载不到音频（预签名 URL 过期 / 非公网可达）。
   本模块的 `failureReason()` 会在这种情况下补一句说明，
   **但会明确标注是推测而不是引擎原话**——不能把猜测伪装成错误码。

3. **`X-DashScope-Async` 头缺失会返回 403**（实测，不是 400）：
   `{"code":"AccessDenied","message":"current user api does not support synchronous calls"}`。
   错误码叫 `AccessDenied`，容易被误判成密钥问题，实际只是少了一个头。

4. **两级 `end_time` 语义完全不同**。任务级 `output.end_time` 是**字符串日期**
   （`"2026-09-15 20:09:09.141"`），句子级 `sentences[].end_time` 才是**毫秒整数**。
   按名字盲取会得到垃圾时间戳。

5. **任务级 `SUCCEEDED` 不代表这条成功**。官方：「当任务包含多个子任务时，
   只要存在任一子任务成功，整个任务状态将标记为 `SUCCEEDED`，需通过 `subtask_status` 字段判断」。
   本模块只提交单文件，但仍逐条检查 `subtask_status`。

6. **结果与下载链接只活 24 小时**。所以不能"先存 URL 稍后再取"，
   必须在轮询到成功的当次就把 JSON 拉下来并落库。

### 3.2 一个文档没写、但实测存在的结构：嵌套 `output`

成功响应的 `output` 里**嵌了一个同名的 `output`**，里面是重复的一份
`results` / `transcription_url` / `subtask_status`：

```
output
├─ task_id / task_status / submit_time / scheduled_time / end_time   ← 任务元信息
├─ output                    ← 冗余的同名嵌套
│   ├─ results[0].transcription_url
│   └─ transcription_url
├─ file_url
├─ usage.duration
├─ request_id
├─ results[0].transcription_url          ← ✅ 有效路径在这里（外层）
└─ transcription_url
```

冗余但**无害**——关键是有效路径是 `output.results`（外层），不是 `output.output.results`。
本模块读外层，实测能正确拿到 `transcription_url`。
`output.task_metrics` 在新域名文档里有，但**实测这个响应里没有这个键**，
所以不要依赖它（本模块不读）。

### 结果 JSON 结构（官方「识别结果说明」样例）

```json
{
  "properties": {
    "audio_format": "pcm_s16le", "channels": [0],
    "original_sampling_rate": 16000,
    "original_duration_in_milliseconds": 3834
  },
  "transcripts": [{
    "channel_id": 0,
    "content_duration_in_milliseconds": 3720,
    "text": "Hello world, 这里是阿里巴巴语音实验室。",
    "sentences": [{
      "begin_time": 100, "end_time": 3820,
      "text": "Hello world, 这里是阿里巴巴语音实验室。",
      "sentence_id": 1,
      "speaker_id": 0,
      "words": [{ "begin_time": 100, "end_time": 596, "text": "Hello ", "punctuation": "" }]
    }]
  }]
}
```

映射到本模块的 `ProviderSentence`：

| 结果 JSON | ProviderSentence |
| --- | --- |
| `sentences[].text` | `finalSentence` |
| `sentences[].begin_time` / `end_time` | `startMs` / `endMs` |
| `sentences[].speaker_id` | `speakerId` |
| `transcripts[].text` | 整段 `result` |
| `properties.original_duration_in_milliseconds` | `audioDuration`（÷1000 成秒） |

**多音轨**：返回多个 `transcripts`（每个带 `channel_id`）。本模块只提交单声道，
但代码按 channel 归并而不是只取第 0 条——否则哪天有人把 ffmpeg 参数改成双声道，
结果会**静默少一半**。

### 说话人分离的前提

官方：说话人分离**仅支持单声道**音频，且**建议音频时长不超过 2 小时**。
本模块 `FfmpegMediaTool.extractAudio` 抽出的就是 16k 单声道 WAV，
前提满足；时长上限 `MEDIA_MAX_DURATION_MS` 默认 2 小时，正好卡在建议值上。
`speaker_count` 可取 2–100，只能辅助算法、不保证输出该人数。

## 4. 本模块的接入方式与代价

阿里云这条路的**唯一硬代价**是：**必须先把音轨变成公网可访问的 URL**。
这直接冲撞契约的一条设计——契约 §3 要求模块自己下载媒体并核验 SHA-256，
而把 `sourceUrl` 转手交给第三方下载，等于放弃"引擎读到的就是我校验过的那份字节"这个结论。

本模块的做法：

1. **照旧自己下载、核验 sha256、抽音轨**，一步不少；
2. 把**抽好的音轨**（不是原始录像）交给 `AudioStaging` 换成预签名 URL；
   45 分钟 16k 单声道 WAV 约 **86 MB**（32000 B/s × 2700s），
   同长度 1080p 录像 1.0–1.7 GB——差一个数量级，上传时间与存储成本都由这个选择决定；
3. 用该 URL 提交、轮询，**轮询结束后**才删除暂存对象
   （引擎可能在排队期间才来拉音频，提交完就删会让任务以一个含糊的下载失败告终）。

契约里 `sourceUrl` 与 `urlExpiresAt` 两个字段、以及幂等指纹**故意排除**它们的设计，
本来就是为这条路预留的——所以这是顺着设计走，不是打补丁。

### 当前状态：暂存是"显式缺席"

`AsrConfiguration.audioStaging()` 目前返回 `InlineAudioStaging`，
它对任何暂存请求**明确抛错**，错误信息写清了下一步该做什么。

为什么不让它"回退到 sourceUrl"把功能凑出来：那样一旦生效，
模块就会在不核验引擎读了什么的前提下声称完成了 sha256 校验。
这种错误**不报错、只失真**，而且失真发生在"我们下载到的字节"与"引擎读到的字节"之间，
从外部完全看不出来。宁可让它响亮地失败。

启动时 `AsrStartupCheck` 会打一行 ERROR 说明"提供方只收 URL 但暂存没实现，
该状态下每个转写任务都会失败"——让问题在启动那几行里暴露，而不是等第一个任务。

**待定**（等主项目确认课程媒体存储形态）：

| 选项 | 前提 | 代价 |
| --- | --- | --- |
| 基于对象存储的 `AudioStaging`（推荐） | 有一个 bucket 与写入凭证 | 上传 86MB/课 + 一份临时副本 |
| 复用主项目已有的媒体桶 | 主项目愿意给写入前缀 | 需与主项目约定前缀与清理策略 |
| 直接把 `sourceUrl` 转给引擎 | 该地址本身公网匿名可读 | sha256 核验语义失效，**不建议** |

## 5. 文档值与实测值

> 实测环境：2026-09-15，公共域名 `dashscope.aliyuncs.com/api/v1`，
> 模型 `qwen-audio-3.0-asr-flash-filetrans`，
> 音频为阿里云官方样例 `hello_world_male.wav`（3.87 秒中文，公网 URL）。
> 复现入口：`src/test/java/.../asr/client/ManualAliyunLiveTest.java`（默认跳过，
> 设 `MANUAL_ASR_TEST_KEY` 后运行）。

| 项 | 文档值 | **实测值** | 结论 |
| --- | --- | --- | --- |
| 提交路由 | `POST {base}/services/audio/asr/transcription` | HTTP 200 + `output.task_id` | ✅ 一致 |
| 轮询路由 | `GET {base}/tasks/{task_id}` | HTTP 200；不存在的 ID 返回 `task_status=UNKNOWN`（**不报 405/404**） | ✅ **确认为 GET**，原先的 GET/POST 矛盾解决 |
| 轮询方法错了会怎样 | — | 未测（已确认 GET 正确） | — |
| `X-DashScope-Async` 是否必需 | 必需 | 去掉 → **HTTP 403** `AccessDenied: current user api does not support synchronous calls` | ✅ 必需，但错误码是 403 不是 400 |
| `parameters` 是否必需 | 新域名下必需 | **公共域名下省略整个 `parameters` 也 SUCCEEDED** | ⚠️ **与文档不符**；代码按更严的规则发（见下方注释） |
| 提交响应是否同步返回结果 | 文档两处表述不一致 | **纯异步**：只回 `task_id` + `PENDING`，无结果 | ✅ 异步两步式 |
| `channel_id` 类型 | `list[int]` | 发标量 → 提交 200 但任务 **FAILED**；发数组 → SUCCEEDED | ⚠️ **必须数组，见 §3.1** |
| `language_hints` 是否被 filetrans 接受 | ⚠️ 官方只在 paraformer-v2 参数表里列出 | **接受**：`["zh","en"]` 与 `["zh"]` 均提交 200 且 SUCCEEDED | ✅ **矛盾解决：filetrans 接受它** |
| `diarization_enabled` | 未在 filetrans 参数表列出 | **接受且生效**：结果里出现 `speaker_id` | ✅ 可用 |
| `speaker_count` 越界（传 1） | 范围 2–100 | 不报错、任务仍 SUCCEEDED | ⚠️ 服务端不校验，代码只发合规值 |
| `vocabulary_id` 传不存在的 ID | — | 不报错、任务仍 SUCCEEDED | ⚠️ **静默忽略**，热词配错不会有人告诉你 |
| `transcription_url` 是否可直接下载 | 是（预签名） | HTTP 200，**无需 Bearer**，可直接 GET | ✅ 一致 |
| 结果 JSON 结构 | `properties` + `transcripts[].sentences[]` | 完全一致；`begin_time`/`end_time` 为**毫秒整数** | ✅ 一致 |
| 句子级 `speaker_id` | 开说话人分离才有 | 一致，键为 `speaker_id` | ✅ 一致 |
| 任务级 `task_metrics` | 新域名文档里有 | **本响应里没有这个键** | ⚠️ 不要依赖它（本模块不读） |
| 成功响应有嵌套 `output` | 文档未提 | **确实存在**，`output.output` 是冗余副本 | ⚠️ 读外层 `output.results`，见 §3.2 |
| 音频不可达的报错 | — | 任务 FAILED，**只有 `output.code=SERVER_ERROR`，无 message** | ⚠️ 信息量极低，见 §3.1 |
| 模型名不存在 | — | 提交阶段 **HTTP 400** `InvalidParameter: Model not exist.` | ✅ 提交期就失败，不会变成坏任务 |
| 端到端耗时（3.87 秒音频） | 官方称"数百倍加速" | 提交→SUCCEEDED **2.3–3.6 秒**；状态序列 `PENDING → RUNNING → SUCCEEDED`（轮询间隔 2s 时可能直接看到 `RUNNING`） | ✅ 短音频接近实时 |
| **实际识别质量（字准率）** | 无公开值 | **未测**——样例音频只有一句话 | ❌ 需真实课堂音频 |
| **2 小时长音频的稳定性** | 未标注 | **未测** | ❌ 需真实长音频 |
| **12 小时 / 2GB 是否硬上限** | 是 | **未测**（成本太高） | ❌ 不打算测 |
| 说话人分离建议 ≤2 小时 | 官方建议 | **未测** | ❌ 需真实长音频 |

> **关于 `parameters` 必需性的一处实测反例**：官方说新版专属域名下必须传 `parameters`
> （空也要 `{}`），否则"任务可正常提交，但识别将失败"。
> 我们在**公共域名**下省略 `parameters` 后任务**成功**了。
> 两种可能：①该限制只对专属域名生效；②文档过时。
> **无法区分**，因为我们没有专属域名的 WorkspaceId 可用。
> 代码选择照更严的规则发——代价只是一个空对象，而规则要是真生效，代价是每个任务都失败。

> **`language_hints` 值得打开**：原先因为"官方参数表只列了 paraformer-v2"而默认留空，
> 实测 filetrans 接受它并正常出结果。所以中英混说的课可以放心配
> `ALIYUN_ASR_LANGUAGE_HINTS=zh,en`。
> 但**注意这只证明"被接受"，不证明"更准"**——
> 这个项目在抬头率模块上已经吃过一次"被接受≠有效果"的教训
> （见 `headup` 的实测记录）。要断言它提升字准率，得用真实课堂音频做对照。

> **一个顺带发现的可用性差异**：这个 `sk-ws-…` 形态的 Key 在
> **OpenAI 兼容端点** `/compatible-mode/v1/models` 下能列出 251 个模型，
> 但其中**没有任何 filetrans 长音频档模型**（只有 `qwen-audio-3.0-asr-flash`、
> `qwen3-asr-flash`、`fun-asr-flash-2026-06-15` 这些 5 分钟档）。
> 也就是说**兼容模式端点不能用来做课堂长音频转写**，
> 必须走本文这条原生 DashScope 通道。

### 离线测试覆盖了什么

20 个用例全部走真实 `HttpServer`（不联网、不消耗额度），覆盖：
请求头与请求体形状、`parameters` 必须存在、`language_hints` 空时不发、
内联音频被拒、轮询状态迁移、`subtask_status` 失败判定、未知状态不判死、
结果 JSON 解析（毫秒时间戳 / speaker_id / 多 channel 归并 / 静音空分段）、
`transcription_url` 缺失、结果下载失败可重试、凭证与 `workspaceId` 缺失提示、
baseUrl 解析、重试分类。

**没有覆盖的**：真实百炼接口的字段名是否与文档一致。那只能靠真机验证——
写进离线测试只会变成"用我的假设验证我的假设"。
