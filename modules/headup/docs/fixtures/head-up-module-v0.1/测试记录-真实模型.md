## 4. 复现性实测（重要）

同一媒体、同一配置、同一 `min_legible_ratio`，连续跑两次：

| 窗口 | 第 1 次 | 第 2 次 | 是否一致 |
| --- | --- | --- | --- |
| win-001 | 4/7 legible 0.778 | 5/7 legible 0.875 | ❌ 差 1 人 |
| win-002 | 6/8 | 6/8 | ✅ |
| win-003 | 18/18 | 18/18 | ✅ |
| win-004 | 7/9 | 7/9 | ✅ |
| win-005 | 1/3 | 1/3 | ✅ |
| **平均抬头率** | **0.6865** | **0.7151** | ❌ 差 **2.9 个百分点** |

单帧重复调用也观察到同类抖动：win-004 同一帧 3 次调用得到 `up=6/down=2`、`up=6/down=1`、
`up=7/down=2`，其中一次 `legible_ratio=0.600` **正好跨过 0.60 阈值**（窗口质量会翻转）。

**结论**：

1. VLM 输出**不是逐位可复现**的（即使 `temperature=0`）：同一帧的判读有约 ±1 人量级的抖动；
2. 靠近阈值的窗口可能在 `VALID` 与 `LOW_QUALITY` 之间翻转；
3. 单次运行的均值建议视为**±3 个百分点**量级的估计值，不要当成精确到小数点的测量值；
4. 用户看到的报告来自**某一次固定 job 的固定 revision**（契约保证终态不可变），所以页面数值本身
   是稳定的；变的是"重跑一次会略有不同"。

## 5. 提示词对照实验（是否应该禁止"推测"）

发现：win-002 是"多人仅见后脑"的俯拍画面，现行提示词却报了 `head_up=4` —— **看不到脸却当成了抬头**。
于是做了一次对照（每窗 2 次，共 20 次调用）：

| 窗口 | 现行 `headup-prompt-1` | 严格版（看不见眼睛一律 unknown） |
| --- | --- | --- |
| win-001（正面） | 4/3/2 → VALID（两次一致） | 4/3/2、4/2/2 → VALID |
| win-002（俯拍只见后脑） | 4/2/7 → LOW_QUALITY | **0/0/12**（不再猜）→ LOW_QUALITY |
| win-003（教室全景） | 18/0/0 → VALID | 18/0/0 → VALID |
| win-004（活动场景） | 7/2/6 → VALID | 5/2/8 → LOW_QUALITY |
| win-005（竖幅全景） | 1/2/2 → VALID | 1/2/2 → VALID |

（单元格含义：`head_up / head_down / unknown`）

**读法**：

- 严格版确实**消除了"背对镜头也算抬头"的问题**（win-002：4 → 0）；
- 代价是有效窗口覆盖下降（win-004 从 VALID 变 LOW_QUALITY），可能让整堂课"无可计算数据"的比例升高；
- win-003 两版都报 18/18（100% 抬头）——说明即便严格提示词，**模型对"全班整齐抬头"这类画面仍偏乐观**，
  这不是提示词能单独解决的，需要人工标注集才能定量评估。

**本轮决策：不改默认提示词**。改判定规则等于改观测口径，属于三方评审范围（见 §6 第 1 项）。
严格版提示词已保存在 `.work/prompt_compare.py`，随时可作为 `headup-prompt-2` 启用。

## 6. 成本与耗时（真实用量）

单帧实测（1280×720、JPEG 200 KB、提示词如现行版本）：**1140 prompt tokens + 约 46 completion tokens**。

| 模型 | 单帧耗时 | 单帧成本 | 45 分钟课（每 10 秒一帧 = 270 帧） | 270 帧总耗时 |
| --- | --- | --- | --- | --- |
| `qwen3-vl-plus` | ≈1.6s | ≈$0.00023 | ≈**$0.062（¥0.45）** | ≈7 分钟 |
| `qwen3-vl-flash` | ≈0.9s | ≈$0.00006 | ≈**$0.015（¥0.11）** | ≈4 分钟 |

（价格取官方文档输入 ≤32k 档：plus `$0.144/$1.434`，flash `$0.036/$0.359` 每百万 token；汇率按 7.2 估算。）

**成本结论：不构成瓶颈**。真正的时间成本是抽帧 + 网络往返；`windowMs=10000` 时整体吞吐约为
**视频时长的 1/4（plus）到 1/6（flash）**，45 分钟课约 4–7 分钟出结果。

## 9. 本轮**没有**验证的事

1. **真实课堂录像**（连续运动、真实远场拾音画面、真实遮挡变化）——本轮素材是照片拼接的静态场景；
2. **识别精度**：没有人工标注集，无法给出"模型对不对"的定量结论（准确率/混淆矩阵都没有）；
3. **长视频**（45 分钟级）的实际吞吐与内存表现；
4. **模型限流/超时**在真实配额下的行为（假服务覆盖过 429/5xx，真实配额未触发）；
5. **多人密集场景**（50–100 人）的计数偏差；
6. **`windowMs` 取值**对结果稳定性的影响（本轮只用 10000）。
